# BE-D06 wire, database, legacy and frontend mapping

Reviewed against the checked-in Laravel resources, actions, migrations and current generated contract on 05/11/2026. This is a source mapping, not a production-data audit or approval to backfill ambiguous records.

| Domain | API wire field | Database/source mapping | Legacy/status note | Frontend impact |
|---|---|---|---|---|
| Program | `customer_id` | `programs.customer_id`; `owner_tutor_profile_id` is separate and comes from the acting Tutor profile. See [`ProgramResource`](../../../../../backend/app/Http/Resources/ProgramResource.php), [`CreateProgramDraft`](../../../../../backend/app/Actions/Programs/CreateProgramDraft.php), and [domain alignment migration](../../../../../backend/database/migrations/2026_10_22_000000_align_program_schema_with_domain_design.php). | Migration derives a Customer only when the legacy invitations resolve to exactly one unique Customer; it fails on ambiguous/missing mapping. Legacy Program `pending` is mapped to `draft`. No additional backfill is proposed. | Treat `customer_id` as the Program's assigned Customer; do not infer it from Tutor ownership or a current Invitation. Consume `allowed_actions` and `version` from the response. |
| Invitation | `customer_id`, `program_version`, `offer_snapshot`, `status` | `customer_id` maps from `program_invitations.invitee_user_id`; `offer_snapshot.target_customer_id` records the snapshotted Program customer. Snapshot is persisted in `program_invitations.offer_snapshot`. See [`InvitationResource`](../../../../../backend/app/Http/Resources/InvitationResource.php) and [Invitation schema](../../../../../backend/database/migrations/2026_10_07_000400_create_program_and_learning_tables.php). | Migration maps legacy `active` Invitation to `accepted`. Pending Invitations whose `expires_at` has elapsed are serialized as `expired`; the read does not itself run expiry. | Read `customer_id` as the target user ID. Render the offer from the immutable snapshot, not the mutable Program. Handle `expired` as an effective API status. |
| Submission | `submission_version`, content/status/timestamps/feedback and file IDs | `task_submissions` stores version rows; `tasks.current_submission_id` points to the current row. See [`TaskController`](../../../../../backend/app/Http/Controllers/Api/V1/TaskController.php) and [versioning migration](../../../../../backend/database/migrations/2026_10_22_073016_add_submission_versioning_and_idempotency.php). | Legacy rows are backfilled as version 1 with a generated UUID idempotency key and current pointer when consistent. That generated key is not evidence that a historical HTTP request can be replayed. | Use `submission_version` for history and `expected_submission_version` for writes. Current Submission can be `null`; do not use the backfilled key to synthesize a client retry. |
| Fee | `period`, `period_start`, `period_end`, `amount_minor`, `currency`, `status`, `tutor_payment_mark` | `period` is derived from `fee_records.period_start` (`YYYY-MM`); other fields map to the corresponding Fee columns. Current payment mark fields are added by [BE-D04 workspace migration](../../../../../backend/database/migrations/2026_11_01_233000_add_be_d04_workspace_schema.php), and output is shaped by [`FeeRecordResource`](../../../../../backend/app/Http/Resources/FeeRecordResource.php). | Legacy `declared_status` was renamed to `status`. Migration refuses legacy `confirmed`/`cancelled` values because their meaning is ambiguous; it requires valid month boundaries, VND and an unmarked initial payment state. Do not infer paid from `confirmed`. | `period` is a display/API convenience, not a separate DB field. Keep declared `status` independent from Tutor's payment mark; zero amount must stay unmarked. |
| Session | `id`, schedule fields, `status`, `version`, nullable `actual` | `id` refers to `program_sessions.id`; nested `actual.id/status/started_at/ended_at` comes from the related `lesson_sessions` row (`lesson_sessions.program_session_id`). See [`SessionResource`](../../../../../backend/app/Http/Resources/SessionResource.php), [base schema](../../../../../backend/database/migrations/2026_10_07_000400_create_program_and_learning_tables.php), and [K04 handover](../../../BE-K04-handover.md). | Migration maps legacy `program_sessions.status=planned` to `scheduled`. Laravel's separate persistence table named `sessions` is unrelated. A planned Session need not yet have an actual LessonSession. | Keep schedule and actual lesson separate in the UI; `actual` is nullable. Use Program timezone for schedule display and parse returned timestamps as UTC RFC 3339. |
| Report | API `reason_code`, `description`; response `status`, assignment and resolution fields | Create maps `reason_code` → `reports.reason` and `description` → `reports.details`; `reporter_id`, `resource_type`, `resource_id`, handling and timestamps persist on `reports`. See [`ReportController`](../../../../../backend/app/Http/Controllers/Api/V1/ReportController.php) and [Report schema](../../../../../backend/database/migrations/2026_10_07_000500_create_operations_and_trust_tables.php). | API names intentionally differ from storage names. H04 report statuses and assignment metadata are surfaced through the workflow projection; no legacy semantic conversion is authorized by this mapping. | Send the API names (`reason_code`, `description`), not DB names. Treat evidence as a separately permissioned endpoint; summary fields do not grant evidence access. |
