## Changes and evidence

- Monitoring dashboard now sends threshold events to Slack rather than claiming local receiver delivery as operator notification. It uses verified HTTPS, a timeout, per-resource cooldown and delayed retries, and distinguishes HTTP 200/`ok=false` from successful delivery. Failure records contain fixed codes, not credentials. Original successful Slack responses are stored separately from requests. The live controlled test sent a labelled synthetic CPU 81/80 threshold through this path; it was not a real resource incident. [Original response and permalink](evidence/teacher-feedback-2026-11-28/summary.json) provide independently inspectable evidence for 3(f)/5(d).
- Production template enables monitoring alerts. Supply `SLACK_BOT_USER_OAUTH_TOKEN` and `SLACK_BOT_USER_DEFAULT_CHANNEL`, run the existing Slack queue worker, and keep suppression off. On the monitored host run `python3 docker/monitoring/dashboard.py --slack-env-file /private/path/production.env --prefix tutorlink-`. The dashboard binds localhost; use an SSH tunnel. Do not commit the env file. On a macOS Python installation without a configured CA bundle, set `SSL_CERT_FILE=/etc/ssl/cert.pem`; TLS verification is never disabled. `--test-alert` sends one clearly labelled synthetic threshold and exits; it is an explicit real Slack send.
- Eight relational factories now cover Catalog, Tutor/Customer profiles, ServiceListing, AvailabilityRule and Program, alongside User role states. The guarded deterministic LocalDemoDataSeeder uses these factories while retaining lookup keys and original local-only checks. It was executed twice after fresh migration in a separate disposable database; counts and test evidence are linked below. Approval factory state does not bypass real document eligibility.
- Upload uses configured private storage, checks quota while holding the owner row lock, and limits request frequency. Program URLs, public text and Listing money have server validation bounds. API behavior and limits are in [the API guide](../api/README.md#28112026--teacher-feedback-hardening-96).
- Marketplace invalidation uses statement transition tables to avoid no-op and irrelevant User/File/Program writes. Catalog generation is separate. Updates that change visibility still invalidate within the writing transaction; the existing multi-connection test verifies old data before commit and immediate denial after commit. ETag/304 saves repeated response bodies, with a regression proving an old ETag cannot revive a withdrawn Listing.
- A synchronous PostgreSQL generation/expiry query remains intentionally. Caching that version for a time window would weaken immediate withdrawal semantics. This work reduces unnecessary version updates and response transfers; it does not claim removal of every database read or elimination of every write contention point.
- Next.js/Caddy set security headers. Next permits the configured API and Reverb origins; CSP allows inline bootstrap/style for static rendering. Backend permits eval for the existing Filament/Alpine runtime. These are compatibility policies, not strict nonce CSP. HSTS applies on HTTPS; local HTTP Chrome checks verify header presence, not browser HSTS enforcement. The login smoke test reported no script errors/CSP violations; Caddy validation passed.
- Issues #31/#32 now describe problem/acceptance criteria and clearly label retrospective clarification. #31/#32/#94/#96 have labels/milestone; #96 is assigned to the implementation owner. Issue/PR templates prompt acceptance evidence and another member's review. Historical commits/reviews are not rewritten or fabricated.
