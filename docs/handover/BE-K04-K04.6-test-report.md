## 5. Bằng chứng cạnh tranh khóa PostgreSQL

`runPair()` giữ khóa Program ở parent, sau đó:

1. Khởi động worker A và đọc PostgreSQL PID từ `READY`.
2. Kiểm `pg_blocking_pids(A)` có PID parent.
3. Khởi động worker B và kiểm `pg_blocking_pids(B)` có PID A.
4. Chỉ nhả khóa Program sau khi xác nhận cả hai điều kiện.
5. Chờ hai worker kết thúc, kiểm exit code, kết quả và trạng thái database.

Chuỗi `block_chain` trong evidence có thứ tự `[worker B, worker A, parent]`. Các PID là ba backend PostgreSQL khác nhau, không phải thứ tự suy ra chỉ từ thời điểm khởi động process. Code có deadline chờ khóa, timeout cho worker và cleanup trong `finally`.

### 5.1. Ma trận kết quả race

Status bên dưới được liệt kê theo thứ tự worker đã xếp hàng, không phải danh sách đã sort.

| Race | Số case | Kết quả ghi nhận | Invariant đã kiểm |
|---|---:|---|---|
| Complete × complete, cùng/khác key | 2 | `[200, 200]` | Một actual, một audit complete, Session version 2, response tương đương |
| Complete trước cancel; cancel trước complete | 2 | `[200, 409]` | Chỉ action đầu thắng; trạng thái/actual đúng với action đó |
| Create trước Program complete/cancel | 2 | `[201, 409]` | Program còn Active; lịch scheduled tồn tại và chặn terminal; không tạo actual |
| Program complete/cancel trước create | 2 | `[200, 409]` | Program terminal; không tạo lịch mới hoặc receipt create thành công |
| Session complete/cancel trước Program complete/cancel | 4 | `[200, 200]` | Session được xử lý trước; Program kết thúc sau khi hết blocker; actual đúng theo action Session |
| Program complete/cancel trước Session complete/cancel | 4 | `[409, 200]` | Program bị blocker scheduled; sau đó Session xử lý thành công; Program vẫn Active |
| Edit × edit cùng expected version | 1 | `[200, 409]` | Chỉ nội dung đầu được ghi, version tăng một lần, một audit update |
| **Tổng** | **17** | **Tất cả đạt** | Có đủ evidence trong cả hai lượt |

Hai complete trả `200/200` là kết quả mong đợi: một transition thật, request còn lại replay. Cùng key có một receipt cho lệnh đó; khác key có thể có hai receipt, nhưng business side effect vẫn một lần.

## 6. Side effect, replay và rollback

- Complete tạo actual `completed`, planned thành `completed`, tăng Session version đúng một lần và ghi audit cùng metadata/receipt trong transaction.
- Cancel giữ lịch sử planned, không tạo actual; audit lưu reason theo contract.
- Replay kiểm quyền hiện tại trước khi trả snapshot; không suy replay chỉ từ status terminal legacy.
- Receipt 30 ngày và metadata terminal có mục đích khác nhau. Metadata cho phép replay tương đương khi dùng key mới hoặc receipt đã hết hạn.
- Receipt mới khi replay bằng key mới được phép. Actual, audit nghiệp vụ, event và version không được tăng theo lần replay.
- Theo [K04.1](BE-K04-K04.1-contract.md), Session chưa phát notification/outbox. Test kiểm số outbox Session không tăng; notification của Program terminal được kiểm riêng theo resource Program.
- Fault tests của transition gồm 7 trường hợp: complete lỗi ở actual/audit/metadata/receipt và cancel lỗi ở audit/metadata/receipt. Sau lỗi, planned vẫn scheduled/version cũ, actual không tồn tại, metadata chưa ghi và không còn audit/receipt transition ghi một phần.
- Fault tại audit create Session cũng chứng minh rollback planned và receipt create.

## 7. Giới hạn kiểm chứng và cảnh báo

- Race mới chạy ở tầng action/database bằng hai process PHP độc lập. HTTP middleware, Request và quyền API được kiểm trong các feature test riêng; đây không phải hai browser hoặc hai HTTP server process gửi đồng thời.
- Harness chủ động xếp thứ tự hai writer, xác nhận chờ khóa rồi kiểm cả các thứ tự quan trọng. Không coi đây là load test, benchmark, kiểm chứng mọi interleaving hoặc bằng chứng không thể xảy ra deadlock trong mọi tải vận hành.
- Fault tests dùng exception từ query listener tại các bước ghi bắt buộc. Chưa diễn tập mất máy, mất điện, SIGKILL hoặc lỗi hạ tầng production.
- Metadata terminal legacy chưa đủ dữ liệu vẫn bị từ chối replay; không tự tái dựng hoặc nhận replay chỉ vì status giống nhau. Lượt này không backfill lịch sử production.
- Kết quả áp dụng cho Docker local và PostgreSQL test riêng. Chưa chứng nhận staging/production, UI, trình duyệt hoặc notification delivery worker.
- Log có cảnh báo Docker Compose về orphan containers do dùng chung project với các service ứng dụng. Hai lệnh test vẫn exit `0`; cảnh báo này không phải lỗi testcase. Lượt lập báo cáo không xóa container.
- Không thêm attendance, video integration hoặc Session attachment.
