# API contract

`openapi.json` is generated from registered Laravel `/api/v1` routes with Scramble. Treat it as a generated release artifact and export it from code instead of editing the JSON by hand.

This is the contract for the **currently registered API**, not the complete target design. The [API Route Catalog](<../Architecture & Technical Design/API Route Catalog.md>) lists both registered and planned routes with status; Product/Domain rules and PRDs define intended behavior. Scramble and route parity do not verify those business rules. `GET /sanctum/csrf-cookie` and `POST /broadcasting/auth` are infrastructure routes outside `/api/v1` and are therefore absent from this file. K03.13 verifies the latter with session/CSRF, current account/membership, session-scoped private-channel authorization and live Reverb logout/suspension/recovery. It remains outside OpenAPI. POST /api/v1/conversations/{conversation}/realtime issues the channel for the current browser session. The artifact now has **123 operations**: the prior 89 plus 16 BE-D04 routes (Overview, Progress, Announcement and Fee), 17 BE-H04 trust operations and the BE-H05 scoped Admin dashboard. The 16 D04 operations were exported from the test branch and checked for route parity, response/error schemas and headers; this is test evidence; the actual local Docker runtime was applied and smoke-tested in D04-22/23, with no staging/production claim. See [BE-D04 D04-18 evidence](../handover/evidence/be-d04/consolidated/test-assurance-release-15-20.md#d04-18) and [K03.13 evidence](../handover/BE-K03-K03.13-test-report.md); Echo/UI is deferred under K03.12.

BE-D03: `PUT /tasks/{task}/submission` retains its per-version UUID `Idempotency-Key` policy. Both feedback POST routes require a UUID `Idempotency-Key` and use the shared 30-day receipt by Tutor/key/method/path/canonical payload. A matching replay returns the stored 200 response after current authorization; a different path or payload returns 409. The feedback response snapshot contains the Task `version`, Submission `submission_version`, decision and feedback metadata, without submission content or file IDs. [BE-D03 test report](../handover/BE-D03-issue-74-test-report.md) distinguishes SQLite evidence from PostgreSQL race evidence still needed.

Authentication uses a Sanctum session cookie. A browser first calls `GET /sanctum/csrf-cookie`, then sends credentials with the session cookie. State-changing requests also send the `X-XSRF-TOKEN` header derived from the `XSRF-TOKEN` cookie. The generated `sessionCookie` security scheme marks routes requiring a session; public routes remain unauthenticated. Missing authentication returns 401; an invalid or expired CSRF token returns 419. Do not automatically replay a state-changing request after 419. The session cookie name comes from Laravel's `session.cookie` configuration at export time. The API contract does not advertise token authentication.

From `backend/`, export using a guarded PostgreSQL test database after configuring the isolated test connection:

```sh
php scripts/test-console.php check
php scripts/test-console.php openapi:export
npx --yes @redocly/cli@2.60.0 lint ../docs/api/openapi.json --config ../.redocly.yaml
php scripts/verify-openapi-routes.php
```

D04 migrations require PostgreSQL. H04 enables guarded PostgreSQL export and updates the CI export step accordingly; database name/host/connected-identity safety checks remain mandatory. The previous SQLite export recipe is no longer compatible with D04. Never export by migrating an application/production database. CI export checks schema/routes, not business correctness; the D04 legacy preflight and fixture suites require their documented preparation rather than a single unprepared mixed-suite invocation.

The seven D23 Admin endpoints remain in the target [API Route Catalog](<../Architecture & Technical Design/API Route Catalog.md>). They are planned, not registered yet, so they are absent from this generated contract. Settle each endpoint's permission, scope, request/response and audit behavior before implementation; then register the route, test it and regenerate this contract. Do not hide a registered route from the contract merely because implementation is incomplete.

## BE-K04 Session integration

Six registered routes provide list/create under `/programs/{program}/sessions`, detail/PATCH under `/sessions/{session}`, and POST `/sessions/{session}/complete` and `/sessions/{session}/cancel`. Session IDs always refer to `program_sessions.id`; `actual` is nullable and nested. Owner/current member may read; only the active Tutor owner may mutate. Create/edit require Active and edit requires scheduled. Paused allows complete/cancel of scheduled Sessions. Terminal Program blocks new mutations while authorized equivalent replay returns its original snapshot.

All four mutations require a UUID `Idempotency-Key`. Edit/complete/cancel also require JSON integer `expected_version`; stale/conflicting requests return 409. Create starts at version 1 without an actual; a changed edit or terminal transition increments once. An unchanged PATCH does not increment version or write another audit. Complete creates one actual atomically; cancel creates none. Replays do not add actual/audit/event/version. Receipts last 30 days; durable terminal metadata supports equivalent complete/cancel replay with a new key or after receipt expiry, subject to the original actor/action/payload. Legacy terminal records without metadata cannot infer replay from their status.

Timestamps use UTC/RFC 3339 with microseconds and the Program timezone context. Optional meeting URLs must be HTTPS, at most 2,048 characters, without credentials. Cancel accepts optional nullable reason up to 2,000 characters. No attendance, video integration, Session attachment or automatic completion is added. Schema migration requirements, PostgreSQL evidence, remaining OpenAPI inference limits and review steps are in the [BE-K04 handover](../handover/BE-K04-handover.md).

## BE-H02 integration

H02 adds `PUT /api/v1/admin/tutor-profiles/{tutorProfile}/assignment` and the two `POST /api/v1/admin/verification-documents/{document}/{approve|reject}` routes. These require the new `admin.tutor_profiles.assign` and `admin.verification_documents.decide` permissions respectively. Existing Admin accounts are not automatically granted either permission; the relevant coordinator/identity owner must provision them through the agreed account-management process.

Assignment requests contain `assigned_admin_id` (nullable for revocation), the current `assignment_version`, and a nonblank `reason` (2–2,000 characters). The selected Admin must be active and have profile view/decision permissions. The response contains assignment metadata only. Reassign/revoke increments `assignment_version`; stale requests return `409 stale_assignment_version`. Assignment permission alone does not grant profile, document, or decision access.

Profile and document decisions require `assignment_version` and `reason`. A profile revision decision additionally supplies `expected_version` for the submitted revision. Profile decisions require current assignment and `admin.tutor_profiles.decide`; document decisions require current assignment and the separate document-decision permission. Out-of-scope profile reads/decisions return 404; missing action permissions return 403. File download still requires profile view, current assignment and the separate document-download permission. Reviewer metadata access and downloads are audited.

`GET /api/v1/admin/tutor-profiles` defaults to `scope=mine` for viewers and `scope=unassigned` for assignment-only coordinators. `scope=all` and `scope=unassigned` require assignment permission and return minimal assignment metadata. Scope filters apply before pagination/counts; the response includes `meta.current_page`, `meta.total`, and `meta.per_page`.

Tutor submit now requires a complete owned avatar, active specialization, headline/bio and a complete private identity card/passport; structured `qualification_claims` require corresponding degree/certificate evidence. Claims contain only `type` (`degree`/`certificate`) and `name`. Profile approval requires approved, unexpired evidence; `other` is not identity evidence. Document replacement creates a separate row and preserves existing decisions.

For an approved profile, PUT profile/avatar edits create a private revision and leave the approved profile unchanged. The first edit omits `expected_version` or sends 0; further edits send the current revision `version`. Tutor GET profile returns the approved fields and the latest `revision` with its `payload`, `status`, and `version`. Submit changes the editable revision to submitted and increments its version. Approve copies the reviewed payload into the live profile atomically; request-changes/reject preserve the live profile. Rejected profiles/revisions cannot self-resubmit. A still eligible assigned reviewer is retained on resubmit; otherwise the profile returns to the unassigned queue with an incremented assignment version.

Profile suspension requires profile permission; if the account is active it additionally requires account-suspension permission and changes both resources, audit, token/session revocation and the profile outbox record in one database transaction. Restore uses `status_before_suspension` and leaves account restoration separate. Suspension/restore does not require assignment. These responses intentionally contain only profile/account state. The H02 migration backfills previously suspended profiles as approved because the legacy endpoint could suspend only approved profiles. No migration or deployment on shared/staging/production databases is implied by test evidence.

H02 PostgreSQL regression coverage includes concurrent assignment writers and Accept-vs-atomic-profile-suspend using independent processes. Listing moderation races and Session/Task writer races remain with their respective modules. Public marketplace visibility/cache/query work remains BE-D05; the H02 checklist and Program eligibility checks do not certify those public surfaces.

## BE-H03 Invitation lifecycle

`POST /invitations/{invitation}/reject` requires the active target Customer; `POST /invitations/{invitation}/cancel` requires the active Tutor owner. Both accept only optional nullable `reason` (string, max 2,000 characters), return `data: InvitationResource`, and require a pending, unexpired Invitation with a Draft Program. Unknown fields return 422; out-of-scope actors get 404; expired or terminal Invitations return 409 without another audit/outbox write. A supplied reason is stored in `audit_logs.reason`, excluded from the notification payload. Requiredness of reasons remains a Product review item; this runtime accepts omission. These endpoints do not require an Idempotency-Key; repeated terminal decisions return 409.

`php artisan invitations:expire` is scheduled every minute with overlap prevention. It uses the same Users (ascending ID) → TutorProfile → optional Listing → Program → Invitation lock order as accept, rechecks time under lock, and records each expiry/audit/outbox/chat synchronization in one transaction. System audit uses a null actor and notifies the Tutor. Failed records roll back independently, produce a nonzero command result and are retried on the next minute; successful records are not processed again. The existing `scheduler` and `outbox-worker` services in `compose.workers.yml` must run in the deployment environment. GET effective expiry remains read-only. No public expire endpoint or schema migration is added. See [BE-H03 report](../handover/BE-H03-issue-75-test-report.md) for PostgreSQL races, rollback and Task integration evidence.

## BE-H04 trust APIs

Seventeen Review/Report/Audit routes are registered. Review create and Report create use UUID Idempotency-Key with canonical validated flat JSON and 30-day receipts; replay checks current scope before returning a snapshot. Keys reused with different method/path/payload return 409. New Review needs completed Program and the target Customer with active membership; unique Program/Customer prevents duplicates. Moderation requires admin.reviews.moderate, expected_version and nonblank reason. Public list/aggregate excludes hidden Reviews; Customer identity becomes the neutral label Customer đã xác minh, default 20/max 50.

Report create permits only Customer/Tutor and readable resource types; reason_code maps to reports.reason, description to reports.details. One open Report per reporter/resource, 10/hour and 30/day; matching replay does not count. Report list/detail for reporters is owner-only; Admin reads require admin.reports.view and current assignment. Coordinator GET admin/reports?scope=unassigned or all requires admin.reports.assign and returns only ID/status/assignee/version. Assignment uses assigned_admin_id, assignment_version and reason; targets must be active Admins with view+decide. Resolve/dismiss requires current assignment, admin.reports.decide, assignment_version and resolution_note, and records decision/audit/outbox atomically.

Evidence requires an open Report and current assigned active Admin with admin.reports.view on every read. Message evidence contains only message ID/body/time for the reported message, up to 10 preceding and 5 following messages in the same Conversation ordered by (created_at,id). Other evidence projects fields by resource type and related moderation history. It never includes emails, verification documents, object keys, File IDs/download URLs or arbitrary attachment content. Missing resources return evidence_unavailable. GET is private/no-store; closed Reports deny evidence while summary/conclusion remains available within scope.

Audit reader requires admin.audit_logs.view and current scope: assigned Reports, assigned Tutor Profiles, or Reviews when also a Review moderator. Other resource types fail closed until a scope source is defined. State/visibility values use an enum allow-list and versions must be bounded integers; no raw JSONB or nested values pass through. Reads append audit.read; there are no PATCH/PUT/DELETE Audit APIs. Existing outbox:purge keeps Audit 24 months; closed Reports older than 24 months from handled_at can be purged by an operator with existing purge permissions plus admin.reports.purge, recording report.purge. Open Reports never purge. See [H04 report](../handover/BE-H04-test-report.md) for test groups and limitations.

H04 validation/scope/state failures use the common code/message/request_id/errors envelope. Unexpected failures return internal_error without SQL/trace. Numeric route constraints reject malformed IDs with 404. These renderers are scoped to H04 paths; other modules keep their existing behavior.


## BE-D05 / BE-H05 runtime contract

`GET /admin/dashboard` requires a browser session, an active verified Admin and `admin.dashboard.view`; each resource aggregate additionally requires its existing resource permission. Profile/Report queues use current assignment or an explicitly permitted unassigned coordination scope. No identity/evidence/raw audit JSONB is included. Existing Admin routes remain registered; future Filament resources must call the shared business actions. Filament 5 is installed but no panel/login/resource UI is registered before Gate BE.

Public marketplace surfaces share verified/active account, approved/not-suspended Profile, approved/unexpired required documents and eligible Listing/catalog/hold gates. Public Tutor receives `listings_page` (default 1), at most 10 minimal cards, and `listings_meta` (page/per_page/has_more/next_page). Avatar remains null pending a policy-authorized public File route. Assigned Profile list defaults to 20, max 50; allowed sorts are `submitted_desc` and `id_desc`.

Anonymous public catalog/marketplace GET JSON 200 responses use a server cache with TTL 60 seconds; database transaction generation and document-expiry boundary are part of the key. Header `X-Marketplace-Cache` reports HIT/MISS/BYPASS. HTTP `Cache-Control: public, no-cache, must-revalidate` forces clients/proxies to revalidate eligibility; `Vary: Cookie, Authorization` prevents mixing contexts. Cookie/Authorization/authenticated requests and other API responses are `private, no-store`; errors are never public-cached. Cache failures use the live database. See [D05/H05 handover and evidence](../handover/BE-D05-BE-H05-handover.md) for schema delta, direct-action/HTTP checks, benchmark limits and migration of existing Admin routes.
