# TutorLink documentation workflow

Read `docs/README.md` before changing product, domain, module, workflow, architecture, or API documentation.

Read `docs/UNRESOLVED_DECISIONS_2026-10-20.md` before claiming the documentation has no open decisions. It distinguishes resolved contradictions from Product/technical choices that still need approval; proposed defaults are not approved behavior.

- Treat `docs/api/openapi.json` as the generated description of registered Laravel `/api/v1` routes. Generate it with Scramble from backend code; never edit the JSON manually. A matching route does not prove its business behavior is complete.
- Treat `docs/Architecture & Technical Design/API Route Catalog.md` as the canonical target API method/path inventory. All listed routes, including the seven D23 Admin routes, remain in scope; the status column distinguishes registered from planned routes. Follow Catalog method/path when updating PRDs or implementing new routes. Do not present planned routes as callable APIs; `docs/api/openapi.json` remains the generated contract for registered routes.
- Keep business rules in Product/Domain and the relevant PRD. When a product decision changes, reconcile affected PRD, lifecycle, workflow, architecture, and Catalog descriptions in the same documentation change; record any implementation gap explicitly. Do not change Catalog status to “Đã đăng ký” until method/path appears in the generated OpenAPI, except runtime-verified infrastructure routes outside `/api/v1`: the Sanctum CSRF bootstrap and `POST /broadcasting/auth` (K03.11). Record their route/session/CSRF evidence in the Catalog and handover; do not count them as OpenAPI operations.
- When backend implementation changes a route, verify behavior with suitable tests, regenerate OpenAPI via `docs/api/README.md`, then reconcile the Catalog status. Do not infer behavior or approval from successful Scramble export or route parity alone.
- The `OpenAPI 0.2.0 draft` guide records a historical target snapshot. Use its decisions as context, check later product decisions, and do not treat its old operation counts, links, or contract as current implementation evidence.
- The 20/10/2026 product decision in BR-10 permits the Tutor owner to create, edit a Draft, and publish Announcement while Program is Active or Paused. Completed/Cancelled block create and publish. This rule is a target behavior until the relevant backend routes and tests exist.
- BR-11 limits Admin Report chat evidence to the reported message plus at most 10 earlier and 5 later messages from the same Conversation. Require `admin.reports.view`, current assignment and an open Report on every read; audit access and deny evidence after closure or reassignment. Keep the evidence route planned until backend implementation and tests exist.
- BR-12 settles M01/D04: Customer age 15+ and Tutor 18+ at registration and DOB edit from the profile UI via `/me`; registration requires explicit consent to the displayed terms version and stores version/time; registration creates an unverified account without a login session; email verification precedes login; resend verification works without login with a neutral response and rate limit; successful password reset revokes previous sessions. Several registered routes still implement older behavior, so keep target and runtime clearly distinct until backend/frontend changes and Scramble regeneration are tested.
- BR-13 settles M01/D09: Customer Profile is optional and owner-only for an active Customer. GET without a row returns `profile: null`; PUT upserts supplied fields, omission preserves the current value and explicit null clears a nullable field. Avatar attachment requires a complete File with matching owner/purpose; replacing or clearing the reference does not delete the old File. `full_name` and `date_of_birth` remain User fields on `/me`. Both Customer Profile routes are still planned, not registered.
- BR-14 settles M03/D06: PublicTutor has the M03-F08 field allow-list, a policy-authorized avatar and at most 10 visible Listings per `listings_page` on the existing GET Tutor route. Tutor slug is generated once with an ID suffix and stays unchanged on name edits; no redirect is needed. The owner may PATCH an active Listing; revalidate, audit and publish the new content immediately without altering existing Program/Invitation snapshots. Restoring User/Tutor Profile only recalculates visibility: already-active Listings reappear when all gates pass; Tutor-inactive Listings remain hidden; archived stays terminal. Admin moderation-hold restore is a separate state transition under M03-F10. Current backend/OpenAPI does not yet satisfy every BR-14 rule.
- BR-15 settles M03-F10 Listing moderation for MVP: an active internal Admin with `admin.listings.moderate` may moderate all Listings, with no per-Listing/category/Report assignment. Hide moves active to inactive under a separate hold; restore automatically returns it to active only when all public gates pass and Tutor has not independently paused it. Missing gates in that case return conflict and retain the hold; Tutor-paused Listings may have the hold removed while remaining inactive. Hide/restore require allowed reason_code and nonblank reason, audit and an in-app Tutor notification after success. Appeals use manual support; do not invent an appeal API. New Program Drafts/Invitations referencing a held Listing are denied; existing Program/snapshots remain unchanged. BR-18 settles acceptance of a preexisting pending Invitation: block accept with conflict while source Listing is held, keep Invitation/snapshot pending and unchanged, allow accept after hold removal only before expiry. Both Admin routes remain planned, not registered.
- BR-16 settles M02/D10: Tutor submission requires an active verified account, headline, bio, active specialization, valid avatar and one valid identity card or passport. Structured qualification claims require corresponding degree/certificate evidence; `other` does not replace identity. The currently assigned active Admin needs `admin.verification_documents.decide` for per-document decisions, separate from download; rejection needs a reason. Required documents must be approved and unexpired before Profile approval. An expired required document removes public/new-service eligibility without suspending User/Profile or cancelling existing Programs. Replacing a file creates a new document row; approving it recalculates visibility. Edits to approved Profiles live in a separate pending revision while the prior approved version remains public. Rejected submissions/revisions cannot be self-resubmitted in MVP. On resubmission, retain a still eligible assignment, else return to unassigned queue. The document-decision routes remain planned; backend/schema/OpenAPI do not yet implement this target.
- BR-17 settles M04/D11: `POST /api/v1/conversations` takes `peer_user_id` and optional `context_listing_id`, not a client direct_key/sender_id; return only minimal peer identity and the originally stored context, without private peer data. Validate any supplied Listing, but store context only on first creation and never overwrite it on reuse/reopen. Suspension does not remove membership/history or change ConversationStatus. The suspended participant cannot log in or read/send even with an old session; the other active participant may still read their own chat history, including cancelled conversations. After restoration the member can read history again. Sending must still pass M04-F04 policy at write time. Admin remains outside membership and only gets BR-11 Report evidence. All chat routes remain planned, not registered.
- BR-18 settles M05/D12: Program offer version increments on successful Draft edits; PATCH/send require `expected_version`; Invitation stores immutable snapshot/version and locks Draft while pending. Expiry is 72 hours in UTC and accept is valid only while server time `< expires_at`; expiration worker lag does not extend it. Cancel Draft and its pending Invitation atomically. Cancel Active/Paused only after scheduled Sessions and nonterminal Tasks are explicitly handled; otherwise return blockers, never cascade-cancel child history. A pending Invitation from before Listing moderation hold stays unchanged but accept is blocked during hold; it can be accepted before expiry after hold removal if Customer/Tutor eligibility passes; do not require the source Listing to become active again because the offer snapshot is locked. Require one atomic accept outcome and PostgreSQL race tests across accept/expire/cancel/suspend/moderation before implementation. M05 routes remain planned, not registered.
- BR-19 settles M06–M08/D21–D22: Paused blocks new Session/Task/Fee, Session edits and Task content edits; existing scheduled Sessions can complete/cancel; already assigned Tasks can start/submit and receive feedback; Tutor may cancel todo/in_progress Tasks. Existing Fee may be edited only while declared and not marked paid. Announcement Drafts can be edited/published in Active/Paused; published Announcement is immutable and corrections use a new Announcement. Use integer `version` plus `expected_version` for edits/actions; stale writes return 409 without partial writes. Submission keeps D13 `expected_submission_version` and Idempotency-Key. Terminal Program resources are read-only. Routes remain planned until implemented and documented from code.
- BR-20 settles Workspace data across M06–M08/M10: `Program.timezone` is authoritative (IANA, default `Asia/Ho_Chi_Minh`); store instants in UTC and expose RFC 3339. Session `meeting_url` is optional HTTPS, max 2,048 characters, no credentials. Overview has all five TaskStatus counts and Program-level `capabilities`; latest summaries have deterministic ordering and use null when empty. Progress MVP is Tutor-estimated integer `progress_percent` 0–100, versioned/audited on edit and never deleted. Submission canonicalization, content/feedback limits, Announcement field limits and Workspace file limit (max 5 files/resource, 5,000,000 bytes/file under the later BR-21/K03.1 decision, PDF/JPG/PNG/DOC/DOCX) are in Business Rules and the M06/M07/M08/M10 PRDs. Fee month follows Program timezone; legacy `confirmed` requires data review before migration. Details live in `Domain Documentation/Business Rules.md` BR-20 and the M06/M07/M08/M10 PRDs. These remain target rules until runtime/schema/API is implemented; keep Catalog routes planned and generated OpenAPI sourced from code.
- M03-F09 allows a verified active Tutor with a non-suspended Profile to manage private Availability before Profile approval. Public visibility still requires an eligible approved Profile. Suspension preserves saved rules while denying management and public visibility. BR-12's verified-login target is not yet fully enforced in backend; do not add a Profile-approval gate to the private Availability API.
- M04-F01 allows either Customer or Tutor to open a Conversation with the opposite role, subject to the eligibility and optional Listing-context gates in that PRD. Reuse the one Conversation per pair; do not infer Customer-only creation from older wording in the historical OpenAPI guide.
- The current SPA authentication contract uses a Sanctum session cookie and CSRF. Scramble must describe that flow from source configuration; do not hand-edit the generated JSON or imply that API tokens are required for Next.js.
- BR-21–BR-27 were approved on 20–21/10/2026; read `Domain Documentation/Business Rules.md` and `UNRESOLVED_DECISIONS_2026-10-20.md` before reopening any of them. Messaging/Files uses the BR-21 quota and the later K03.1 technical file validation without automatic antivirus; new uploads are limited to 5,000,000 bytes/file. Fee Record has BR-22 replay, zero-fee and notification rules. D08 generic command replay is BR-23: UUID key, canonical payload, 409 on mismatch, 30-day receipt; Submission, Messaging and Fee keep their specialized policies. BR-24 fixes Review/Report limits and Report evidence allow-list/24-month retention. BR-25 fixes outbox retry, alert, replay and retention; audit action/scope/24-month retention. BR-26 fixes API error/timestamp/money/pagination conventions and NFR target values. BR-27 fixes Admin users/metrics permissions, scope and DTO. These are target decisions; DB migrations, API runtime, generated OpenAPI and performance evidence remain separate implementation work.
- `Architecture & Technical Design/Database Design — TutorLink.md` is the target schema reference for BR-12–BR-27, including Tutor Profile revisions, Listing moderation hold, idempotency receipts and Outbox replay. Keep any linked draw.io diagram aligned with this schema when specifically asked to update that diagram; do not infer SQL migration status from either document.
